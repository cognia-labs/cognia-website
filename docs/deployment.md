# Deployment

The deployable artifact is `out/`, generated by `pnpm build`. The application has no server routes or runtime Next.js dependency. Canonical links, sitemap, OpenGraph links and docs links are baked into this artifact; rebuild for each public origin.

## Cloudflare Pages: GitHub Actions

1. Create a Cloudflare Pages Direct Upload project with production branch `main`. Use your chosen project name; no Cloudflare project is created implicitly by this repository.
2. Create GitHub Environments named **staging** and **production**. Configure the following values in each environment. Repository-level values may supply shared defaults, but put environment-specific origins and project names in their respective environments.

| Kind     | Name                    | Value                                                                   |
| -------- | ----------------------- | ----------------------------------------------------------------------- |
| Variable | `CF_PAGES_PROJECT`      | Your existing Pages project name; may be shared or environment-specific |
| Variable | `CLOUDFLARE_ACCOUNT_ID` | Account containing that project                                         |
| Variable | `WEB_SITE_URL`          | Public HTTPS website origin, no path                                    |
| Variable | `DOCS_SITE_URL`         | Public HTTPS documentation origin, no path                              |
| Secret   | `CLOUDFLARE_API_TOKEN`  | Token limited to this account with Account / Cloudflare Pages / Edit    |

3. Run **Deploy website**, select `staging` (the default) or `production`, and choose the source ref. Production accepts only `main`; staging can validate and deploy a feature branch. The workflow installs from the standalone lockfile, validates configuration, runs lint/typecheck/tests, builds, and uploads `out/`. Deployments are serialized separately for each environment.

| GitHub Environment | Pages deployment branch | Public origin used at build time          |
| ------------------ | ----------------------- | ----------------------------------------- |
| `staging`          | `staging`               | `staging` environment's `WEB_SITE_URL`    |
| `production`       | `main`                  | `production` environment's `WEB_SITE_URL` |

When sharing one Pages project, `staging` is a Pages preview branch, normally served at `https://staging.<project>.pages.dev`; configure that exact origin or your staging custom domain. If using separate projects, keep their configured production branch as `main`, so the staging upload remains a preview deployment. The docs origin can be shared if the documentation has only one deployment. Add production environment protection/review rules to match your team's release policy.

First run with **dry_run=true** to report environment mapping and missing configuration. Dry-run never installs, builds or uploads, and a green dry-run means the inspection ran successfully, not that the cloud configuration is complete or the website was deployed. A real deployment fails before build/upload when required configuration is missing. The notifier likewise treats this result as `not-deployed`.

```sh
gh workflow run deploy.yml --ref main -f environment=staging -f dry_run=true
gh workflow run deploy.yml --ref main -f environment=production -f dry_run=true
# After configuring and checking the selected environment:
gh workflow run deploy.yml --ref main -f environment=staging -f dry_run=false
```

The old `CF_WEB_PAGES_PROJECT` variable is now named `CF_PAGES_PROJECT`. GitHub does not copy variables, environment settings or secrets between repositories. See [workflow notifications](notifications.md) for the independent Feishu setup.

No deployment is automatic on pull requests or product-source changes. To enable automatic production deployment later, add a `push` trigger after configuring and reviewing your deployment policy.

For direct CLI deployment, export the public build values and Cloudflare credentials through your shell or secret manager, then run:

```sh
export NEXT_PUBLIC_WEB_SITE_URL=https://your-website.example
export NEXT_PUBLIC_DOCS_SITE_URL=https://your-docs.example
# Set CLOUDFLARE_ACCOUNT_ID and CLOUDFLARE_API_TOKEN securely in your environment.
pnpm deploy:pages --project-name your-pages-project --branch main
```

The commands use the lockfile-pinned Wrangler. `pnpm deploy:pages` validates public origins, builds, then runs `wrangler pages deploy out`; additional flags are forwarded to Wrangler. Local `.env.local` is not loaded by `deploy:check`; export these two variables explicitly.

Alternatively, connect this repository directly in Pages: root directory `/`, build command `pnpm deploy:check && pnpm build`, output directory `out`, Node 26 and pnpm 11.18.0, with the same public environment values. Use a Pages build image supporting those tool versions; the GitHub Actions Direct Upload path controls them explicitly. Preserve `public/_headers` and the generated `out/_redirects` in the output so `/en/*` canonical redirects and hashed-video caching apply. Configure custom domains and `www` redirects in Pages after deployment.

## Container

The image builds the same static export and serves it with the included dependency-free Node static server as the unprivileged `node` user. It supports clean URLs, 404 pages, `/en` redirects, content types, immutable assets, HEAD and byte-range media requests.

```sh
docker build \
  --build-arg NEXT_PUBLIC_WEB_SITE_URL=https://your-website.example \
  --build-arg NEXT_PUBLIC_DOCS_SITE_URL=https://your-docs.example \
  -t cognia-website:local .
docker run --rm -p 3002:3002 cognia-website:local
```

Browse `http://localhost:3002`, then check `curl -f http://localhost:3002/zh/product`. Changing build arguments requires a rebuild; runtime variables cannot rewrite static metadata. CI builds and smoke-tests this image on Linux. The container exposes port 3002; place TLS and any custom-domain routing at your reverse proxy.

## Other static hosts

Upload `out/`. Configure clean routes (`/product` → `/product.html`, `/zh/product` → `/zh/product.html`), `/en` → `/` and `/en/*` → `/*` permanent redirects, a real `404.html` response with HTTP 404, content types, and video byte ranges. `_headers` and `_redirects` are Pages conventions; other hosts need equivalent configuration. The included static server implements those rules for local/container use.

## Rollback

Keep the last successful artifact or image digest. Roll back to that exact deployment in Pages, or redeploy that artifact/image. Preserve its public origin configuration. A source rollback alone does not change an existing cloud deployment.

## 中文

构建产物为 `out/`，可部署到静态托管或容器。GitHub Environments 分别配置 `staging` 和 `production`，两者使用同名变量和 Secret，但地址、项目可不同。手动运行 Deploy website 时选择环境：staging 对应 Pages 的 `staging` 预览分支，production 对应 `main`，且生产来源只允许 `main`。先用 `dry_run=true` 检查环境映射与缺失配置；dry-run 成功仅代表检查已执行，不代表配置齐全或上线成功。实际发布缺少配置会在构建上传前失败。旧变量 `CF_WEB_PAGES_PROJECT` 已改为 `CF_PAGES_PROJECT`；GitHub 不会跨仓库复制变量和密钥。官网与文档的真实 HTTPS 地址写入构建产物，修改后需要重新构建。飞书通知的独立配置见[通知指南](notifications.md)。Docker 构建也需要这两个地址；运行时修改环境变量不会改写静态页面。其他静态服务需自行支持干净路径、语言重定向、404、正确 MIME 与视频 Range 请求。

Pages redirects are generated by `postbuild` from the canonical origin in `out/index.html`, including `.env.local` or Pages preview values already resolved by Next.js. Pages targets always use a fixed HTTPS origin; in development that host-specific file promotes the built canonical origin to HTTPS. Doubled or encoded slashes cannot redirect to another host. Use `pnpm start` for local HTTP routing, or build with your public HTTPS origin before using the Pages-specific preview. Serve the complete output of `pnpm build`, including `out/_redirects`; do not copy an older redirects file over it. `pnpm preview:pages` runs the actual Pages runtime at port 8788; `node scripts/check-pages-preview.mjs` checks its routes and redirect safety while it is running.
